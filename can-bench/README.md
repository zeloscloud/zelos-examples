# A CAN bench you can run on one machine

Three microcontrollers running real firmware, talking CAN to each other, on a
bus you can watch with `candump`. None of it is hardware.

This is the shape of bench most firmware teams have: a Linux box, a CAN
adapter, a few nodes on the wire, and someone working out why the data looks
wrong. Here the nodes are emulated and the adapter is virtual, so the whole
thing runs in containers.

```
 ┌─────────┐  ┌─────────┐  ┌─────────┐
 │   VCU   │  │   BMS   │  │  DC-DC  │   Zephyr on STM32H753, in Renode
 └────┬────┘  └────┬────┘  └────┬────┘
      └───────── vcan0 ─────────┘         a real SocketCAN interface
                   │
             ┌─────┴─────┐
             │   agent   │ :2300         decodes the bus against bench.dbc
             └─────┬─────┘
                   │
              Zelos app                  on your machine
```

The bench ships two builds of the DC-DC node, differing by one line: one
respects a limit as soon as it is told about it, the other approaches it
gradually. Running the second one produces a fault that no single CAN frame
reveals, which is what the second half of this guide is about.

## What you need

- **Linux with Docker.** The bus is a SocketCAN interface, and SocketCAN is a
  Linux kernel feature.
- On **macOS or Windows**, work inside a Linux VM. Docker Desktop is not
  enough: its kernel has no CAN support, and that cannot be changed from inside
  a container. On macOS:

  ```bash
  limactl start --name=bench template://docker-rootful
  limactl shell bench
  ```

  Editing the repository on your host and running it in the VM works fine. Only
  the running needs Linux.
- [**just**](https://just.systems), which is the interface to everything here:

  ```bash
  curl -fsSL https://just.systems/install.sh | bash -s -- --to ~/.local/bin
  ```

- **2 GB of disk** for the simulator and agent images, and another 1.4 GB if you
  rebuild the firmware.
- A **Zelos account**, for the part that decodes and plots the bus. Everything
  up to that point needs no account.

You do not need a CAN adapter, an STM32, a cross-compiler, or `vcan` configured
on your host. The bench creates its virtual interface inside its own network
namespace and removes it when it stops.

## Start it

The nodes ship prebuilt, so watching the bus needs no cross-compiler:

```bash
mkdir -p build
curl -fL --output-dir build -O "https://github.com/zeloscloud/zelos-examples/releases/latest/download/{vcu,bms,dcdc,dcdc-defect}.elf"
just up
```

Three containers come up: one owns the bus, one runs Renode with the three
nodes, and one runs a Zelos agent that decodes the traffic. It takes about 15
seconds once the images are local; the first run pulls 1.9 GB.

Watch the raw bus:

```bash
just bus
```

```
 (000.000000)  vcan0  300   [8]  3C 05 6E 04 C2 01 54 7A
 (000.251239)  vcan0  200   [7]  95 0E 41 03 9B 02 DF
 (000.003411)  vcan0  100   [4]  01 2C 03 DF
 (000.004805)  vcan0  201   [7]  50 46 00 00 58 02 DF
 (000.005541)  vcan0  300   [8]  3C 05 6E 04 C2 01 54 7C
 (000.234282)  vcan0  300   [8]  3C 05 6E 04 C2 01 54 7E
```

Three senders, five identifiers, and `0x300` arriving twice per cycle of the
others because the DC-DC runs at 50 ms against their 100 ms.

Stop it, leaving nothing behind:

```bash
just down
```

## What the bus carries

`../dbc/bench.dbc` is the single source of truth. The firmware's pack and unpack
code is generated from it, the periods the nodes run at come from it, and the
agent decodes against the same file.

| ID | Message | From | Period | Carries |
|---|---|---|---|---|
| `0x100` | `VCU_Command` | VCU | 100 ms | Requested mode, torque request, heartbeat |
| `0x200` | `BMS_Status` | BMS | 100 ms | Pack voltage and current, state of charge, contactor |
| `0x201` | `BMS_Limits` | BMS | 100 ms | Discharge, charge and auxiliary current limits |
| `0x202` | `BMS_CellVoltages` | BMS | 500 ms | Four cell voltages |
| `0x300` | `DCDC_Status` | DC-DC | 50 ms | Rail voltage and current, pack draw, temperature |

The three nodes form a control loop. The VCU commands a mode. The BMS publishes
the current envelope for that mode, including `AuxCurrentLimit` — the pack
current the DC-DC may draw. The DC-DC respects it.

The VCU walks a fixed drive cycle: stand still, drive, charge, repeat. One pass
is 15 seconds of firmware time, about 75 seconds of wall clock at the speed the
bench runs.

## Layout

```
../dbc/bench.dbc          the wire format, and the source of everything below
../lib/codec_bench/       generated by cantools; committed, never hand-edited
../lib/can/  ../include/  the CAN helper every node shares
../nodes/vcu|bms|dcdc/    three Zephyr applications
bench/                    the agent's config; the images and Renode script are ../bench/
notebooks/                the tests
traces/                   recorded runs the tests check against
```

The firmware lives at the root of the repository, shared with any other bench.
The repository is also a Zephyr module, so the shared library and the generated
codec are built once and linked by all three applications. There is one
implementation of the wire format in the tree.

### Changing the bus

Edit `../dbc/bench.dbc`, then:

```bash
just dbc        # regenerate lib/codec_bench/ from the DBC
just firmware   # rebuild the nodes
just flash good # load what you built
```

The change appears in the firmware, on the wire, and in the app. No bit
position is written by hand, and CI fails if the committed codec stops matching
the DBC.

Periods come from the DBC too: `GenMsgCycleTime` becomes
`BENCH_*_CYCLE_TIME_MS` in the generated header, and each node's loop uses it.

### Rebuilding the firmware

`just firmware` builds in a toolchain image defined in `../toolchain/Dockerfile`
— Zephyr for Arm and nothing else, 1.4 GB rather than the 23 GB of Zephyr's own
CI image. The first run builds it; later runs reuse it.

Each node comes out around 40 KB of flash and 8 KB of RAM on a part with 2 MB
and 512 KB.

## Seeing the decoded bus

Open the Zelos app and connect to the bench:

1. Open the right sidebar — `Cmd+J` or `Ctrl+J`
2. **Data Sources** → **New agent**
3. Enter `localhost:2300`, or `<bench host>:2300` from another machine

The signal tree fills with `vcan0` and every message in the table above.
Double-click a signal to plot it.

Signals are named `vcan0/<id>_<Message>.<Signal>`, for example
`vcan0/0300_DCDC_Status.InputCurrent`. A second source, `vcan0_raw`, carries
every frame undecoded, which distinguishes "no traffic" from "traffic the DBC
does not match".

**If port 2300 is already in use**, `docker compose` fails with `failed to bind
host port`. The Zelos app runs its own agent on that port, so this happens on
any machine where the app is installed. Publish the bench elsewhere:

```bash
BENCH_PORT=2301 just up
```

Running the bench on a headless box and the app on your laptop avoids the clash,
and is how a real bench is usually arranged.

### The bench runs slower than wall clock

Three emulated Cortex-M7 cores share one host CPU. On a 16-core machine the
bench runs at roughly a fifth of real time: a message declared at 100 ms arrives
about every 500 ms.

Serial execution and the 100 µs quantum in `../bench/renode-run.sh` were chosen by
measuring this bench, not copied from an example; the file records what the
alternatives cost. The ratios between messages are exact, so anything that
depends on relative timing is faithful. Anything that depends on absolute rate
is not.

## Finding the defect

Run the other build:

```bash
just flash defect
```

That restarts the simulator with the second DC-DC firmware and gives the agent a
fresh store, so what you see next comes only from this build. Give it a couple
of minutes to get through a drive cycle, then plot two signals together:

- `vcan0/0201_BMS_Limits.AuxCurrentLimit`
- `vcan0/0300_DCDC_Status.InputCurrent`

When the vehicle enters Charge, the BMS drops the converter's allowance. The
draw should be under the new limit at once. Instead it walks down to it, drawing
more than it is allowed for 250 ms: the draw is capped at DEMAND_A (4.5 A) and the charge allowance is 2 A, so it walks 2.5 A at 10 A/s.

Every frame is legal and every value is in range. Nothing logs an error, and no
single frame is evidence of anything: the fault exists only in the shape of two
signals over time.

The cause is in `../nodes/dcdc/src/main.c`, and the difference between the two
builds is the one Kconfig option in `../nodes/dcdc/Kconfig`. The rate cap is there
for a reason — inrush stresses the contactors and the input filter — but it was
applied to reductions as well as increases.

## The tests

```bash
just test
```

Each file in `notebooks/` is a test, and `just test` runs all of them:

- `nodes-are-alive.md` — every node is still transmitting. A silent node
  reports nothing anywhere, so it needs an explicit check.
- `signals-are-plausible.md` — the state of charge is inside its range, the
  cells are within a sensible spread, the converter is not implausibly hot, and
  the low-voltage rail holds near its 13.8 V setpoint. These are the checks
  that catch a scaling mistake in the DBC or a unit error in firmware.
- `dcdc-respects-allowance.md` — the draw exceeds the allowance only in the
  first couple of samples after the allowance changes.

The last one defines that rule once and runs it against two sets of data: a
recorded run of the defective firmware, which it must flag, and the live bus,
which it must find clean. Because the rule is written once rather than copied
into a separate self-test, what passes is the rule itself.

It also waits for the BMS to lower the allowance rather than assuming the bench
has been running long enough, and says so if that never happens.

`traces/dcdc-defect.trz` is that recording. `agent.trace()` opens it with the
same query and check API as live data, and on a trace the file is the clock, so
the assertion means the same thing however fast the simulation runs. Record
another from whatever is on the bench with:

```bash
just record my-run
```

Each notebook is also a report. They chart what they measured, tabulate it, and
end with their verdicts, so the rendered page is worth reading whether it passed
or failed.

`just test` exits non-zero if any notebook fails, and writes a self-contained
HTML page beside each one — `notebooks/nodes-are-alive.html` and so on. Charts
are interactive and the page opens with no network access, because the plotting
runtime is embedded in it. That is most of each page's 900 KB; the data is a
few tens of KB.

CI keeps those pages as a `test-results` artifact on every run, including failed
ones, so a red build comes with the evidence attached rather than just a log.

## What this bench cannot show you

Renode's CAN model implements no acknowledgement and no arbitration: a node
attached to the hub always transmits successfully. Three consequences follow.

- **A bitrate mismatch is invisible.** Nodes at different bitrates work in
  simulation and fail immediately on hardware. The bench sets its bitrate
  explicitly, in one place, for this reason.
- **Bus-off, error frames and error counters cannot be demonstrated.** No
  firmware fault will produce them here.
- **Arbitration and bus loading are not modelled.** Frame ordering under
  contention is not what hardware would do.

The bench does faithfully exercise the firmware, the DBC, the decode path, the
signal model and the workflow.

### Security

The agent has no transport encryption and no client authentication. Anything
that can reach its port can read the data and call the extension's actions. Keep
the bench on a network you trust.

## Going to real hardware

The CAN extension takes a channel name, so pointing it at `can0` instead of
`vcan0` and stopping the Renode container reads a physical adapter instead. That
is the design rather than a tested claim: it is one line of configuration, and
it has not been run here.

## Versions

| Component | Version |
|---|---|
| Zephyr | `v4.4.2` |
| Zephyr SDK | `1.0.1`, Arm only |
| Renode | `antmicro/renode:1.16.1` |
| Zelos agent | `26.0.8` |
| Zelos CLI | `0.1.9` |
| CAN extension | `zeloscloud/zelos-extension-can` `v0.1.15` |
| cantools | `41.3.1` |

Renode is pinned at 1.16.1 for a specific reason: releases before 1.16.0
byte-reversed CAN identifiers through the SocketCAN bridge, so a frame sent with
ID `0x001` arrived on the host as `0x000`.

## Troubleshooting

| What you see | Why | Fix |
|---|---|---|
| The Zelos app will not start | The bench holds `localhost:2300` | `just down`, then start the app, or run the bench with `BENCH_PORT=2301` |
| `failed to bind host port ... address already in use` | Something already has the port | `BENCH_PORT=2301 just up`, and connect to 2301 |
| `just up` fails creating `vcan0` | The kernel has no `vcan` module | Install your distribution's extra kernel modules. On a minimal or immutable kernel, use a VM |
| `RTNETLINK answers: File exists` | A `vcan0` already exists on the host | Harmless: the bench uses its own network namespace |
| `just bus` shows nothing | Renode is still booting three machines | Wait 20 seconds. `docker compose logs renode` shows progress |
| `build/ is older than the sources` | Firmware predates a source change | `just firmware`, then `just flash good` |
| `Unhandled write to offset 0x1C` | Zephyr writes CAN bit-timing bits Renode's model does not implement | Expected and harmless |
| A test fails on `is transmitting` | A node stopped | `just down && just up`. If it repeats, open an issue with `docker compose logs renode` |
